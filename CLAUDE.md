# CLAUDE.md

Project: **Statement Categorizer** (Savvpro take-home). Reads a Pakistani (PKR) bank statement CSV, categorizes every transaction with **our own rule-based code**, flags uncertain rows as **Needs Review**, lets the user fix them.

Hard deadline: 6 hours total. Branch: `candidate-bilalnadeem614`.

## Default stack

- Backend: Python, FastAPI
- Database: Supabase, **only if a database is actually required**. Default is in-memory first. Do not add Supabase unless the user asks or the feature cannot work without persistence.
- Frontend: React / Next.js

## Git rules (strict)

- **Never commit, push, create branches, or open pull requests.** The user does all of this.
- Do not run `git add`, `git commit`, `git push`, `git checkout -b`, `git merge`, `git rebase`, or `gh pr create`.
- Read-only git is fine: `git status`, `git diff`, `git log`.
- When a task is finished, say what changed and let the user commit.

## Python environment (strict)

- Use a conda env named **`assigment`**. Create it if missing: `conda create -n assigment python=3.11 -y`
- Install every Python library inside this env only. Never install into the base env or system Python.
- In non-interactive shells, run commands with `conda run -n assigment <command>` (for example `conda run -n assigment pip install fastapi`, `conda run -n assigment pytest -q`).
- Keep `backend/requirements.txt` in sync with what is installed. Update it whenever a library is added.

## Hard rules (from the task, never break)

1. **No LLM decides a category.** No OpenAI, Anthropic, Gemini or any big AI model anywhere in the categorization path (app code, runtime, tests). The brain is plain Python rules.
2. If the brain is not sure, the row goes to **Needs Review**. A wrong guess is worse than asking.
3. Fake data only. Sample data lives in `sample_statement_pkr.csv` (generated by `gen_sample_statement.py`). No real people, no real statements.
4. Never commit keys, passwords or tokens. Keep `.env` in `.gitignore`. Supabase keys, if used, live only in `.env`.
5. Tests are required (pytest for backend). Brain logic must be covered.
6. Required docs in the repo: `README.md`, `DESIGN.md`, `AI_USAGE.md`.
7. Log AI usage as we go in `AI_USAGE.md`: tool used, how it helped, where it got things wrong, token usage.

## Skills and plugins (installed and ready)

### caveman (terse replies)
- Use `/caveman` mode for normal chat and status updates. Drop filler, pleasantries and long intros.

### ponytail (write less code)
- Before writing code, take the simplest option that fully meets the requirement: skip it if not needed, reuse existing code, use the standard library, use a native feature, use an installed dependency, then write minimal code.
- Read the code and trace the real flow before simplifying. Reduce the solution, not the investigation.
- Leave a `ponytail:` comment where a shortcut has a known limit.
- Never trim: input validation on upload and API boundaries, error handling that prevents data loss, security, or anything required by the task (tests, docs, Needs Review behavior).

### graphify (codebase knowledge graph)
- Build the graph once the first backend modules exist: `/graphify .`
- Before opening many files, read `graphify-out/GRAPH_REPORT.md` for orientation. Use `graphify query "..."`, `graphify path "A" "B"`, `graphify explain "X"` to trace dependencies before editing.
- Refresh after structural changes: `graphify . --update`.
- `graphify-out/` stays in `.gitignore`.

If a plugin fails, say so in one line and continue with normal tools. Do not stall.

## Code conventions

- Python 3.11+, type hints, `ruff` formatting. Pydantic models for API schemas.
- Money in PKR as `Decimal`, never floats. Dates parsed with an explicit `%d-%m-%Y` format.
- Brain rules live in data (a rules list/YAML), logic lives in code. One function per rule type, each unit tested.
- Keep the repo clean: no dead code, no commented-out blocks.
- Frontend stays simple: upload, table, Needs Review filter, inline category edit, category totals.
