## 1. Use case

**Customer:** a small, self-managing residential landlord with 1–4 rental properties, using one business checking account and one credit card. At tax time they need every transaction mapped to **IRS Schedule E** lines, with non-P&L items (transfers, deposits, principal, improvements) kept out of income/expense totals.

Why this use case: it has genuinely hard, realistic ambiguities (mortgage interest vs principal, security deposits vs rent, repairs vs capital improvements, mixed personal/business merchants) which let the brain demonstrate *knowing when it is not sure*.

Disclaimer in app + docs: organizational aid, not tax advice.

### Category taxonomy (data in `backend/rules/categories.yaml`)

**Income**
- `RENT` — Sch E line 3 (rent, late fees, pet fees, prepaid last month)

**Expenses (Sch E lines)**
- `ADVERTISING` (5) · `AUTO_TRAVEL` (6) · `CLEANING_MAINTENANCE` (7) · `COMMISSIONS` (8)
- `INSURANCE` (9) · `LEGAL_PROFESSIONAL` (10) · `MANAGEMENT_FEES` (11)
- `MORTGAGE_INTEREST` (12) · `OTHER_INTEREST` (13) · `REPAIRS` (14) · `SUPPLIES` (15)
- `TAXES` (16) · `UTILITIES` (17) · `OTHER_EXPENSE` (19: HOA, bank fees, landlord software)

**Non-P&L (excluded from Sch E totals, still shown)**
- `SECURITY_DEPOSIT_RECEIVED` / `SECURITY_DEPOSIT_RETURNED` (liability, not income/expense)
- `LOAN_PRINCIPAL` · `CAPITAL_IMPROVEMENT` (depreciable, not expensed)
- `TRANSFER` · `CARD_PAYMENT` · `OWNER_CONTRIBUTION` · `OWNER_DRAW`
- `PERSONAL` (non-deductible) · `INTEREST_EARNED` (not rental income)

**Decision status** (separate from category): `AUTO` · `NEEDS_REVIEW` · `USER_CONFIRMED` · `DUPLICATE`.
**Refunds** keep the original expense category with `is_refund=true` (contra-expense, reduces the category total). Never income.

## 2. System architecture

```
Next.js UI ──HTTP/JSON──> FastAPI ──> Services ──> Ingest ─> Normalize ─> Brain ─> Repository (SQLite/SQLAlchemy)
                                                                     ^
                                                         rules/*.yaml + user MerchantRules
```

Clean-architecture layers (dependencies point inward):
- `domain/` — pure dataclasses/enums: Transaction, Decision, Category, Flag. No framework imports.
- `ingest/` — bytes → `RawTransaction[]`. Format detection, CSV bank profiles, OFX.
- `normalize/` — RawTransaction → Transaction (Decimal amounts, ISO dates, merchant key, direction).
- `brain/` — Transaction[] + context → Decision[]. Pure, deterministic, no I/O. **The graded core.**
- `services/` — orchestration use-cases (process upload, apply correction, summarize, export).
- `db/` — SQLAlchemy 2.0 models, repositories, Alembic migrations.
- `api/` — FastAPI routers, Pydantic schemas, error mapping. Thin.
- `core/` — settings (pydantic-settings), logging (structured JSON), security helpers.

## 3. The brain (own code, deterministic, explainable)

Input: normalized `Transaction` (date, amount: Decimal signed from the *account holder's* view, direction, raw description, merchant_key, account_type: checking|credit_card, memo).
Output: `Decision(category, status, confidence, reasons[], rule_ids[], flags[])`.

Pipeline — each stage proposes scored candidates; nothing is an LLM:

1. **Structural/non-P&L detector** — transfers (`TRANSFER TO/FROM`, own-account masks), card payments (`AUTOPAY`, `PAYMENT THANK YOU` on card), owner draws/contributions. High-confidence, exits early.
2. **Direction logic** — inflow vs outflow sanity. Inflow on an expense merchant ⇒ refund (keep category, `is_refund`). Inflow from a person via Zelle/Venmo/ACH ⇒ rent candidate; memo/keywords `deposit`, `security` ⇒ `SECURITY_DEPOSIT_RECEIVED`. Returned/NSF items ⇒ reversal of linked rent.
3. **User memory** (MerchantRules from past corrections) — highest priority after structural rules; exact merchant_key match.
4. **Exact merchant dictionary** (`merchants.yaml`) — e.g. county tax collector ⇒ `TAXES`, insurer ⇒ `INSURANCE`, utility ⇒ `UTILITIES`, lender ⇒ mortgage.
5. **Keyword/regex rules** (`keywords.yaml`) with weights (`PLUMB`, `HVAC`, `HOA`, `PROPERTY MGMT`, `ZILLOW RENTAL`…).
6. **Fuzzy merchant match** (rapidfuzz token_set_ratio ≥ threshold) against dictionary; score scaled by similarity.
7. **Policy rules / blocking flags** (force review even if a category scored high):
   - `MIXED_USE_MERCHANT` (Amazon, Walmart, Costco, Target)
   - `POSSIBLE_CAPITAL_IMPROVEMENT` (repair/supply candidate > $2,500 de-minimis threshold)
   - `MORTGAGE_SPLIT_REQUIRED` (lender payment: interest vs principal unknowable from statement)
   - `PAYMENT_TO_INDIVIDUAL` (Zelle/Venmo to a person: contractor? personal?) + `POSSIBLE_1099` if YTD ≥ $600
   - `AMOUNT_OUTLIER` (> N× merchant median), `UNPARSEABLE_FIELD`, `AMBIGUOUS_DATE`
8. **Resolver** — combine candidates: `final = top score`; status `AUTO` only if `score ≥ 0.85` AND `margin(top, second) ≥ 0.20` AND no blocking flag. Otherwise `NEEDS_REVIEW` with the top suggestion pre-selected and the human-readable reason. Thresholds in config.
9. **Cross-row passes** — duplicate detection (pending/posted, overlapping uploads via fingerprint), recurring detection (same merchant ± amount monthly ⇒ confidence boost), YTD aggregates for 1099 flag.

Explainability: every decision carries `reasons` like *"Matched merchant 'KING COUNTY TREASURER' → Taxes (rule merchants.taxes.king_county, 0.97)"*.

Learning: a correction with `remember=true` writes a MerchantRule; `apply_to_similar` re-runs the brain on same merchant_key rows in the statement.

Evaluation: `scripts/evaluate_brain.py` runs all `samples/*` against `*.expected.json` and reports **auto-precision**, **coverage (auto rate)**, **review rate**, confusion matrix. Results pasted in DESIGN.md; CI fails if auto-precision < 100% on golden set.

## 4. Edge-case catalog (each ⇒ fixture row + test)

Parsing
- Date formats: `MM/DD/YYYY`, `YYYY-MM-DD`, `DD/MM/YY`; ambiguous order resolved file-wide (any day>12), else flag.
- Amounts: `-45.00`, `(45.00)`, `45.00 CR/DR`, `$1,234.56`, separate Debit/Credit columns, credit-card sign inversion. Always `Decimal`.
- BOM, Latin-1/Windows-1252, `;` delimiter, quoted commas, trailing summary rows, blank lines, preamble rows before header.
- OFX 1.x SGML and OFX 2.x XML; QFX; missing `NAME` falls back to `MEMO`.
- Empty description, zero amount, future date, extremely large amount.
Domain
- Rent via Zelle/Venmo/ACH with tenant names; partial rent; late fee; pet fee; prepaid last month.
- Security deposit received vs rent; deposit returned (not expense).
- Refund from Home Depot (contra-expense, not income).
- Returned/NSF tenant payment (reverses rent).
- Mortgage payment (split required).
- Property tax, HOA, insurance (annual + monthly), utilities, landlord software (rent apps).
- Home Depot $3,400 (possible capital improvement) vs $80 (repair/supply).
- Amazon/Walmart/Costco (mixed use → review).
- Zelle to an individual contractor; 1099 flag at YTD ≥ $600.
- Transfers between own accounts; credit-card autopay (no double-count).
- Pending + posted duplicate; same statement uploaded twice / overlapping periods.
- Interest earned on checking (not rental income); bank fees.
- Merchant noise: `SQ *`, `TST*`, `PAYPAL *`, `POS DEBIT`, store numbers, city/state, card last-4.
Security / abuse
- Oversized file, wrong extension, binary disguised as CSV, zip bomb–style huge row count.
- OFX XML with XXE / billion-laughs payload.
- Descriptions like `=HYPERLINK(...)`, `+cmd`, `@SUM` → neutralized on export.

## 5. Security & production-grade checklist

- Upload: max 5 MB, max 20k rows, extension + content sniffing, decoded in-memory, never executed, never stored raw longer than needed.
- OFX/XML parsed with **defusedxml** (XXE, entity expansion).
- CSV export: prefix-escape `= + - @ \t \r` (OWASP CSV injection).
- Pydantic validation on all inputs; SQLAlchemy ORM only (no string SQL).
- CORS allowlist from config; security headers middleware; request size limit; basic rate limit (slowapi).
- Structured JSON logs with request-id; **no transaction descriptions/amounts in info logs** (PII minimization).
- Config via env (pydantic-settings); `.env.example`; no secrets needed at all.
- Containers: non-root user, slim base, healthchecks, pinned versions.
- Supply chain: `uv.lock`, `package-lock.json`, Dependabot, pip-audit, npm audit, bandit, gitleaks.
- Guard: CI step asserting no `openai|anthropic|google-generativeai|transformers|langchain` in dependencies (proves "the brain is our code").
- Out of scope (documented): authentication/multi-tenancy — single-user local app; design keeps a `workspace_id` seam.

## 6. Testing strategy

- Unit: every brain stage, normalizer, each CSV profile, OFX parser.
- Property (hypothesis): amount parser round-trips, merchant normalizer idempotent, brain never crashes and always returns a valid status.
- Golden: `samples/` end-to-end via evaluate script; precision gate.
- Integration: FastAPI TestClient — upload → list → patch → summary → export.
- Frontend: Vitest + Testing Library (table, category select, summary).
- E2E: one Playwright happy path (upload sample → fix review row → summary updates → export).
- Coverage gate: backend ≥ 85%.

### Token discipline (the "used smartly" evidence)
1. **Contract-first**: schemas + OpenAPI + CLAUDE.md written once; sub-agents read files, not chat history.
2. **Tight briefs**: each spawn gets goal, files to touch, acceptance criteria, "report ≤ 150 words". No open-ended "explore the repo".
3. **Right model per job**: Haiku for mechanical, Sonnet for building/reviewing, Opus only for orchestration + brain. Fable avoided.
4. **Parallel, not iterative**: one review wave with all reviewers concurrently, one fix pass — no ping-pong.
5. **Read-only reviewers** write findings to a file; orchestrator reads only summaries.
6. **MCP/plugin hygiene**: unauthenticated servers (atlassian, datadog, linear, notion, slack) and the failing GitHub MCP disabled for this project; use `gh` CLI instead. Engineering plugin skills invoked only on demand (e.g. `engineering:architecture` for ADRs once), not kept loaded.
7. **Context hygiene**: `/compact` at phase boundaries; Grep over full-file reads; no re-reading files just edited.
8. **Measurement**: after each phase log agent, model, tokens, duration to `docs/ai-log/phases.md`; user captures `/usage` / `/cost` screenshots at each phase end for AI_USAGE.md.
